Start hereHow to study Nix on paper

Nix looks strange until one idea clicks: a package is the output of a pure function, and its path in the store is a hash of every input that went into it. Same inputs, same path. Change anything, and you get a new path beside the old one. NixOS applies that idea to the whole operating system.

$ readlink $(which git)
/nix/store/9lsj6cx2vq2a1f0wb3kz8r5mhd4y7inp-git-2.47.1/bin/git
           ^ hash of all inputs  ^ name-version

The three questions

Ask these of every snippet in the book. Most confusion in Nix comes from losing track of one of them.

  1. Is this the language, a package, or a NixOS option? They look alike but live in different worlds.
  2. What does this expression evaluate to? Write the value in the margin.
  3. What ends up in the store, and who refers to it?
Tip

Keep a notebook page called Option diary. Each time a chapter sets an option like services.openssh.enable, write its full name and type. By Part 5 you will have your own map of the options you use most.

The box types

Worked boxes evaluate code step by step. Terminal boxes print real command output. Tip and Pitfall boxes are habits worth keeping. Exercises end each chapter, with answers under the dashed line: cover them with a card until you have tried.

Flakes

A flake is a folder with a flake.nix that names its inputs exactly and lists what it offers. Lock the inputs and the same flake builds the same thing on any machine, today or in five years.

Chapter 9Anatomy of a flake

A flake.nix is one attribute set with three keys: a description, the inputs it depends on, and outputs, a function that gets the fetched inputs and returns all the flake provides.

{
  description = "My machines and tools";
  inputs.nixpkgs.url = "github:NixOS/nixpkgs/nixos-26.05";
  outputs = { self, nixpkgs, ... }:
    let
      system = "x86_64-linux";
      pkgs = nixpkgs.legacyPackages.${system};
    in {
      packages.${system}.default = pkgs.hello;
      devShells.${system}.default = pkgs.mkShell {
        packages = [ pkgs.go pkgs.gopls ];
      };
      nixosConfigurations.frost = nixpkgs.lib.nixosSystem {
        modules = [ ./hosts/frost/configuration.nix ];
      };
    };
}
Worked: which command reads which output
OutputRead by
packages.<sys>.<name>nix build .#name
devShells.<sys>.defaultnix develop
apps.<sys>.<name>nix run .#name
nixosConfigurations.<host>nixos-rebuild switch --flake .#host
checks.<sys>.<name>nix flake check

.#name means "this folder's flake, output name". With no name, Nix looks for default. The first build writes flake.lock, which pins every input to one commit; commit it too.

Pitfall: the flake only sees files Git knows

You add hosts/frost/configuration.nix, rebuild, and get error: getting status of '/nix/store/…-source/hosts/frost/configuration.nix': No such file or directory. In a Git repo, Nix copies only tracked files into the store. Run git add on the file; you do not need to commit.

Chapter 17Troubleshooting clinic

Each case is an error almost every NixOS user meets in their first months. Read the code, predict the message, then compare your fix with the one given.

Case 2infinite recursion encountered
{ config, lib, ... }: {
  imports = if config.services.nginx.enable
            then [ ./web.nix ] else [ ];
}

Diagnosis

To know config, NixOS must first collect every module, and that means reading imports. But here imports needs config. Neither can be computed first.

Fix: always import, decide inside

# web.nix
{ config, lib, ... }: lib.mkIf config.services.nginx.enable {
  networking.firewall.allowedTCPPorts = [ 80 443 ];
}
Case 3hash mismatch in a fetcher
Terminal
error: hash mismatch in fixed-output derivation
         specified: sha256-AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=
            got:    sha256-p3Kq0bJ1dZ6mYwq8xv2sJ0hTt9nF4cL7aE5uR1iWzGk=

The usual trick when writing a fetcher: put hash = lib.fakeHash;, build once, then paste the got value in. If the hash breaks later, the source really changed upstream.

Case 4a downloaded binary will not start
$ ./tool
Could not start dynamically linked executable: ./tool
NixOS cannot run dynamically linked executables intended
for generic linux environments out of the box.

There is no /lib64/ld-linux-x86-64.so.2 on NixOS. Best fix: package it with autoPatchelfHook (Chapter 13). Quick fix: programs.nix-ld.enable = true;

Chapter 18Recipe book: whole configs

Recipe 4: a website with HTTPS in 14 lines
services.nginx = {
  enable = true;
  recommendedTlsSettings = true;
  virtualHosts."notes.example.org" = {
    enableACME = true;   # get a certificate
    forceSSL = true;     # redirect http to https
    root = "/var/www/notes";
  };
};
security.acme = {
  acceptTerms = true;
  defaults.email = "admin@example.org";
};
networking.firewall.allowedTCPPorts = [ 80 443 ];

One rebuild installs nginx, writes its config, creates a systemd timer that renews the certificate and opens the firewall. Delete the block and rebuild, and all of it is gone again.

Problem 18.2

Module A sets services.openssh.enable = lib.mkDefault false; and module B sets services.openssh.enable = true;. Is SSH on? What if B used lib.mkForce false and a third module set true?

Answer On. A plain value has priority 100 and beats mkDefault (1000); lower numbers win. With mkForce (50) in B, SSH is off: 50 beats the third module's 100.
